# 协作模式：总领 + 主笔 + 杂工

一份讲义或复习页动辄几十万字，让最贵的模型（和用户对话的那个）从读材料写到构建，额度消耗很大。协作模式把活拆给三种角色：总领只写任务说明、做审核和发布；正文交给另一个强模型（主笔）；抽图、查页、写脚本、构建、QA 这些杂活交给便宜的模型（杂工）。2026-10 用这套办法做了复变期末复习页、电子电路主讲义 v4 和期中期末复习页。总领消耗的主要是读交付报告、跑脚本、抽查，比亲自写省很多。

什么时候用：整门课重写、补多次课、复习页、题库这类大活。改几段、修一个错，总领直接做更省。

## 三种角色

| 角色 | 谁来当 | 做什么 | 不做什么 |
|---|---|---|---|
| **总领** | 和用户对话的会话（通常最贵） | 盘点材料，和用户定范围、主线；写任务说明；审核；看原图裁决争议；改共用文件；发布 | 不写正文 |
| **主笔** | 能用的最强模型，跑在独立进程或独立会话里 | 写讲解、概念、易错、结构决定；亲自写或逐题审每道题的解析；设计核验 | 不发布，不动别的课程 |
| **杂工** | 便宜的子代理 | 抽转写和嵌图、找教材页、抄题、写验算脚本、填覆盖表、拼装、构建、QA | 不定结构，不写讲解思路 |

主笔可以是：
- 另一个 CLI 的无头模式跑强模型：oh-my-pi（`omp -p`）、Claude Code（`claude -p`）、Codex（`codex exec`）等。主笔自己的子代理就是杂工。
- 总领所在工具的子代理，指定用最强的模型。子代理的结果会回到总领的上下文，所以只让它交短报告（文件清单和计数），细节写进文件。

## 主笔比总领弱时（常见：只能用子代理）

子代理的能力常常不如总领。这时不要把整门课交出去，按“能不能用脚本验收”来切分：

1. **要判断的部分留给最强的模型。** 包括讲解思路、概念补充、易错、结构和取舍。这些由总领或最强的那个模型写；弱模型可以先起草，总领逐段改。
2. **交给弱模型的活要小、要格式固定、要能脚本验收。** 一个代理只管一个小节或一套卷。产物写到指定路径（md 片段 + json）。验收条件写成数字：核验脚本通过数、`coverage_check`、`format_check`、题目条数。
3. **要求带证据。** 每个结论都附上依据：教材页码、原图路径、脚本项 id。总领抽查时顺着证据看，不用重读材料。
4. **答案用两个代理交叉验证。** 一个解题，另一个独立重算并复核“答案卷错误”。两者不一致时总领裁决。复变题库用这种做法：18 条答案卷错误里 17 条成立，剩下 1 条其实是题干抄漏了。
5. **小模型（Haiku 一类）不看图、不画图。** 概统 v1、大学物理 v4.2 交给 Haiku 的配图都返工了。
6. **数据**：复变期末复习页审出 12 处中间式错误，其中 10 处出自杂工。弱模型交回的解析默认不可信，必须经过逐步核验。

## 任务说明怎么写

任务说明存成 `制作记录/工作资料/<任务>任务说明.md`，同时作为记录保留。主笔用 `@文件` 或把全文贴进提示读入。结构如下：

1. **角色与分工**：你是主笔；哪些必须亲自写或逐题审，哪些派给杂工；杂工交回的内容要审。
2. **禁止的动作**：不要运行同步、部署脚本，不要 git commit/push；不要运行 `build_all.py`，它会重建所有课程。只构建本课：`build_lecture.py <配置>` + `reader/derive.py "<NN 课程>"`。
3. **文件归属**（并行时必写）：列出它能写的文件和不能碰的文件。共用文件（`AGENTS.md`、`03 决策与修订日志.md`、`开始阅读.html`、`00 阅读指南.md`、`材料指纹.json`、同步脚本）由总领最后统一改，要写进去的文字放在主笔的记录里。
4. **先读**：Skill 的 references、本课程制作记录、要模仿的样板（源稿、拼装脚本、核验脚本、记录小节），以及材料路径。
5. **要做的事**：编号列出，写清范围（到哪一节）、主线、编号规则、备份目录。
6. **硬性要求**：
   - 逐步推导核验：每个中间式，不只是最终答案。
   - 覆盖表。
   - 正文不回退：对照备份逐段比较，只允许预期的变化。
   - `format_check` / `desktop_qa` PASS。
   - 记录要写的小节名。
7. **交付报告**：文件清单、题数、核验通过数、各检查结果、仍不确定的地方。
8. 无头运行时加一句：**不要提问等待用户；不确定处按说明处理并记进记录。**

写说明的三条原则：

- **只写要做什么和怎么自检，不写对失败的猜测。** 2026-10-26 的一份补充说明写了“工具结果只显示一行 Read image file”，主笔因此认定自己看不到图，推翻了本来读对的内容。看图类任务要给一个具体的自检，例如“读 p2，确认第 6 题有三个运放 A1、A2、A3”，对上了就继续。
- **总领核实过的事实直接给出。** 比如原图读法写成一份核对文件，让主笔照它更正，不要只写“仔细核对”。
- **源数据也可能错。** 主笔对题库或答案卷提出异议时，总领亲自看原图裁决。电子电路期末题库是在没看图的情况下整理的，6 道大题读错了 3 道。

## 启动与监控

以 oh-my-pi 为例：在项目根目录后台运行，日志写到临时目录。

```bash
omp -p --model <强模型> --thinking high --auto-approve --no-title \
  --add-dir <课程材料目录> --add-dir <教材目录> --add-dir <Skill 目录> \
  --max-time 10h "@制作记录/工作资料/<任务>任务说明.md" "按任务说明完成任务，最后给交付报告。"
```

- `--max-time` 按墙钟时间计，大活给 8—10 小时。
- 会话记录在 `~/.omp/agent/sessions/<项目路径>/*.jsonl`，用脚本解析最近的工具调用就能看进度，不用读全文。
- 中断（超时、电脑关机）后用 `omp -p --resume <session.jsonl> … "从中断处继续；先检查中断时正在运行的子代理有没有交回产物"`。中断时正在运行的子代理不会自动恢复。`--restore` 不能和 `-p` 一起用。
- 其他工具同理：Claude Code 用 `claude -p` 配 `--model`、`--add-dir` 和允许写文件、跑脚本的权限选项；中断后用 `--resume` 接上。
- 两个主笔并行时，按文件归属分开，各自只构建自己那门课。

等待期间不要频繁轮询。总领可以去做别的事，等进程退出或交付报告出来再审。

## 审核（总领，按成本从低到高）

1. **重跑全部核验**：新旧核验脚本都跑一遍，核对通过数和报告一致。
2. **重跑检查**：`format_check`、`coverage_check`、`desktop_qa`；查 MathML merror 为 0、残留 `$` 为 0。
3. **逐段比较**：对照修订前备份，确认只有预期的变化（插入、重排编号）。
4. **抽查**，优先看这几类：
   - 杂工写的解析；
   - 依赖读图的内容；
   - 回忆卷题；
   - 与答案卷不一致的答案。

   抽查时把解析的中间式和核验脚本对应项一条条对照。浏览器里看三四个关键锚点。
5. **小问题自己改**（Edit 后重建本课）。大问题把清单发回主笔，用 `--resume` 继续。
6. **收尾**：
   - 改共用文件。
   - 在主笔的记录末尾加“审核（日期，审核者）”一节，写查了什么、改了什么、还有什么没核到。
   - 发布前只提交本任务的文件，`git diff` 里别的会话的改动要排除掉。

## 常见坑

- 只核最终答案，漏掉中间步骤的错误（复变期末复习页漏了 12 处）。核验必须覆盖每个中间式。
- 主笔顺手跑了全量重建，覆盖了其他会话还没发布的改动。要在说明里禁止。
- 并行会话同时追加同一个共用文件，后写的盖掉先写的。共用文件只由总领改。
- 主笔超时退出，交付报告没写完。先看源稿和记录的实际状态，再 `--resume`。
